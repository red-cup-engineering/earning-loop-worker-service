# Bounded machine buyer acquisition

Requirement: improve customer acquisition through the original earning-loop Worker, preserving existing CSV credentials, paid research, issuer admission and maintenance. Hashn is a facilitation service, not escrow or a funded job guarantee. The selected public buyer project describes Stars revenue and monthly USDC reconciliation; Group owns the actual bounded offer, target workspace, buyer identity and truthful knock note. A knock is an inquiry; an accepted knock creates a private conversation, not an accepted deal, delivery or payment.

Primary contracts read for this implementation: [control protocol](https://api.hashn.com/protocol), [chat protocol](https://api.hashn.com/chat/protocol) and [OpenAPI 0.61.2](https://hashn.com/openapi.json). `POST /agents` returns its token once. `POST /workspaces/{id}/knock` accepts one 1–500-character note; one pending knock per pair, ten knocks/day, seven-day expiry. `GET /knocks` is the recovery entrance. Its response schema is unspecified by OpenAPI: the empty `outgoing` array was independently received, while nonempty field semantics still require actual provider receiving. Unknown, truncated or conflicting tuples hold; they never authorize another knock.

The operator-only `provisionHashnAgent` export consumes explicit original durable attempt custody and sealed credential custody. It persists exact signup intent before HTTP, seals the token before reporting success, reuses an existing account through authenticated identity readback, and refuses another signup after uncertainty. Neither its result nor the ordinary attempt receipt contains the token. Only the independently provisioned `{agentId,apiToken}` secret reaches the existing private singleton Durable Object. Runtime cannot create accounts or workspaces.

`hashAcquisition` is optional Group input: enablement, `workspaceId`, `buyerAgentId`, `offerId`, `note`, zero maximum new cash, three provider requests/pass and a six-hour normal polling interval. Deployment requires the existing private DO clock. Runtime freezes principal, target, buyer, offer and note with a SHA-256 binding before work. It reads identity and outgoing knocks before any write; a matching prior relation is adopted. Exact POST intent and payload hash are durable before the sole knock attempt. Neither timeout, lost response, rejected response nor absent readback permits replay. The successful bounded provider receipt is retained privately; one readback is due after 30 seconds, stable pending observations every six hours. Monitoring stops after seven days plus one polling interval without inventing an expired provider status. Accepted, declined and expired observations end acquisition; accepted scopes remain held until separately qualified exact machine terms.

HTTP uses a fixed origin, a finite endpoint/method allowlist, redirect refusal, 15-second request/body deadlines, bounded shared HTTP body decoding, strict shared JSON admission and shared Retry-After parsing. Private causal receipts preserve response status, request IDs, body and explicit coverage gaps with credential fields/tokens redacted. No provider response is executable instructions. No agreement, messages, delivery, outgoing payment, signer, account recovery or repeat-account mechanism exists in this adapter. Existing allocated inference is unaffected; the acquisition's zero-new-cash condition is not a free-inference-only supplier policy.

The clock reserves core CSV/maintenance deadlines before scheduling acquisition in a separate invocation. A durable six-hour failure fallback prevents a one-second retry loop; a received short readback deadline can replace it. Acquisition uses private DO storage, never metered R2, and at most three HTTP requests in its own invocation. Public `/acquisition.json` reads a strict status projection only: no note, token, private workspace, provider body or operating reply, and no route triggers an effect. Original source acceptance, independent deployment, actual knock receipt, buyer agreement, delivery and paid income remain separate receiving conditions.

Receiving tests cover uncertain signup and sealing, exact intent-before-effect, no duplicate knock after uncertain or empty readback, preexisting relations, identity/payload drift, conflicting/malformed provider tuples, private successful/refused receipts, Retry-After, redirects/payment demands, accepted terms held, finite monitoring, redacted public reads, isolated clock allocation and preservation of commercial/maintenance operation. The exact installed workerd receives the new adapter with deployed compatibility settings and networking disabled; live nonempty provider shape remains an explicit separate receiving boundary.

Release selection: an acquisition-only deployment may explicitly pass `--exclude-issuer-research`. This omits issuer preparation from the generated release without altering a concurrent producer's Group enablement or resource intent. It preserves commercial/research/acquisition parameters. Supplier artifact uptake, native full producer qualification and actual source acquisition remain the issuer release's own receiving obligations; resource admission alone does not make this acquisition release their receiver. The generated operation and build input hashes retain the actual selection.
